# Codex Desktop 26.721 → 26.727 浏览器能力故障复盘

本文记录一次 Windows 上 Codex Desktop 更新后，电脑操控设置中的 Google Chrome 整行被禁用、Browser 和 Chrome 插件无法使用、安装按钮不可点击的完整诊断与恢复过程。

## 结论

这不是 Windows 把 Chrome 权限关闭了，而是 Codex Desktop 判断浏览器控制链路不完整，因此把 Google Chrome 配置项整体置灰。

本次故障同时包含三层版本漂移：

| 层级 | 更新前 | 更新后 |
|---|---:|---:|
| Desktop AppX | `26.721.4979.0` | `26.727.4816.0` |
| Browser/Chrome/Computer Use 插件 | `26.721.41059` | `26.727.40816` |
| 全局 Codex CLI | 独立版本 | `0.144.5` |

`26.727.40816` 是 bundled 插件版本，不是 Desktop AppX 版本。AppX、插件、全局 CLI 和 Desktop 内置 CLI 是相互独立的层级，不应直接比较是否相等。

## 为什么 Google Chrome 整行被禁用

Chrome 控制依赖完整链路：

```text
Chrome 插件
  → Computer Use 运行时
  → Chrome 扩展
  → Native Messaging Host
  → Codex Desktop 后端
```

本次先后出现了两个都能让整行置灰的状态。

### 状态一：旧插件仍在，但新版运行时没有物化

Desktop 已升级到 `26.727.4816.0`，但用户目录仍指向：

```text
openai-bundled-appx-26.721.4979.0
```

已安装的 Browser、Chrome、Computer Use 记录也仍是 `26.721.41059`。当前 Desktop 需要的运行时目录没有生成：

```text
%LOCALAPPDATA%\OpenAI\Codex\bin\d7e8094cfb76a267
%LOCALAPPDATA%\OpenAI\Codex\runtimes\cua_node\fb8898c05a62885e
```

AppX 中的当前资源存在，但 WindowsApps 下的 Application Protected/EFS 属性没有被 Desktop 正确转换为用户侧运行时。界面因此能显示 Chrome 项目，却无法建立可用控制后端。

### 状态二：旧注册被移除，新市场仍未生成

移除旧 `openai-bundled` 注册后，预期 Desktop 会在重启时自动生成：

```text
%USERPROFILE%\.codex\.tmp\bundled-marketplaces\openai-bundled-appx-26.727.4816.0
```

但两次完整重启后该目录仍不存在。此时 Browser、Chrome 和 Computer Use 在 `codex plugin list` 中全部不可发现，界面既没有有效插件源，也无法发起正常安装请求，于是出现整行禁用和按钮不可点击。

移除 marketplace 注册不会删除旧市场和插件缓存；它只会让旧内容失去活动引用。因此这个状态可以恢复，但会造成暂时的浏览器能力完全消失。

## 实际恢复过程

### 1. 恢复当前 Desktop 运行时

使用仓库脚本推导当前 AppX 所需的哈希目录，并从 AppX 资源通过暂存目录恢复：

```powershell
pwsh -NoLogo -NoProfile -NonInteractive `
  -File .\scripts\repair-codex-chrome-runtime.ps1 -WhatIf

pwsh -NoLogo -NoProfile -NonInteractive `
  -File .\scripts\repair-codex-chrome-runtime.ps1
```

恢复后验证了：

- Codex 运行时目录存在且关键文件哈希匹配；
- CUA 运行时共 `4192` 个文件通过递归相对路径和 SHA256 校验；
- 目标目录没有加密条目；
- `codex.exe`、`node.exe` 和 `node_repl.exe` 烟雾测试成功。

### 2. 安全物化当前 AppX marketplace

Desktop 多次重启仍没有生成当前市场，因此采用一次性最后手段：

1. 从当前 AppX 读取 `openai-bundled`；
2. 复制到唯一暂存目录；
3. 使用 `robocopy /A-:E` 去除传播的加密属性；
4. 对 `841` 个文件逐一比较相对路径和 SHA256；
5. 确认目标没有加密条目；
6. 原子移动到 `openai-bundled-appx-26.727.4816.0`。

完整可执行范例见 [Update-safe bundled marketplace](./update-safe-bundled-marketplace.md#manual-copy-last-resort)。

### 3. 切换市场并对账已安装版本

当前市场注册成功后，manifest 已经是 `26.727.40816`，但已安装记录仍显示 `26.721.41059`。因此按依赖顺序执行一次：

```powershell
foreach ($plugin in @('computer-use', 'browser', 'chrome')) {
  codex plugin add "$plugin@openai-bundled" --json
  if ($LASTEXITCODE -ne 0) {
    throw "Failed to install $plugin from the recovered marketplace."
  }
}
```

这是一项一次性缓存对账，不应改造成计划任务或自动同步脚本。

### 4. 让 Desktop 重新生成 Native Host

完全退出 Desktop（包括系统托盘）后重启。当前 Chrome Native Host 名称是：

```text
com.openai.codexextension
```

正确位置为：

```text
HKCU\Software\Google\Chrome\NativeMessagingHosts\com.openai.codexextension
%LOCALAPPDATA%\OpenAI\extension\com.openai.codexextension.json
```

只检查旧键 `com.openai.codex` 会产生“Native Host 缺失”的误报。

## 修复过程中踩到的坑

### 1. 过早移除旧 marketplace 注册

本次先移除旧注册，再等待 Desktop 自动恢复，导致出现一段时间的新旧市场都不可用。

更安全的顺序是：

```text
先物化并校验新版市场
→ 备份 config.toml
→ 移除旧注册
→ 立即注册已验证的新版市场
```

### 2. 反复重启，但没有检查物化结果

正常 Desktop 应在启动时自动恢复，但本机连续完整重启仍没有创建当前 AppX 市场。以后重启一次没有变化，就应转入分层诊断，而不是继续重复重启。

### 3. 只比较 AppX 和 runtime，没有比较 installed 记录

旧健康检查只比较 AppX marketplace 和 runtime marketplace。当前市场恢复后，它可能在已安装记录仍为旧版本时报告健康。

健康脚本现已增加：

```text
InstalledVersion
InstalledMatch
```

已安装插件仍为旧版本时会返回退出码 `1`。

### 4. 使用旧 Native Host 名称检查当前版本

`com.openai.codex` 不是当前 `26.727` Chrome 插件使用的宿主名。优先运行 Chrome 插件自带的 `check-native-host-manifest.js`，由当前插件版本提供预期名称、扩展 ID 和允许来源。

### 5. 把 Chrome 没启动误认为插件损坏

最终检查中扩展和 Native Host 全部正确，但 Chrome 控制仍暂时 unavailable。官方诊断显示 Chrome 进程没有运行。

```text
Chrome running: no
Extension: installed and enabled
Native Host: correct
```

Chrome 没有运行不是插件损坏。启动扩展检查所选中的 Chrome Profile 后，再进行在线控制测试。

### 6. 只相信系统 PATH

系统 PATH 中的 Codex CLI、Node 和 Python 可能来自另一套安装。Desktop 使用的是 AppX 及其哈希运行时。诊断时需要同时检查 Desktop 当前运行时，不能只依赖：

```powershell
Get-Command codex
Get-Command node
```

## 下次更新的快速恢复流程

目标是“一次重启、一次诊断、最多一次手工恢复”。

### 第一步：完整重启一次并运行健康检查

```powershell
pwsh -NoLogo -NoProfile -NonInteractive `
  -File .\scripts\check-codex-browser-health.ps1
```

如果 `RuntimeMatch` 和已安装插件的 `InstalledMatch` 全部为 `True`，不要进行手工修复。

### 第二步：检查当前哈希运行时

```powershell
pwsh -NoLogo -NoProfile -NonInteractive `
  -File .\scripts\repair-codex-chrome-runtime.ps1 -WhatIf
```

只有当前 AppX 对应的运行时缺失时才执行正式恢复。不要硬编码本次的哈希值。

### 第三步：市场缺失时先准备新版，再切换注册

不要先移除仍可回滚的旧注册。先完成当前 AppX marketplace 的暂存、全量校验和原子落位，再在短时间内完成：

```powershell
codex plugin marketplace remove openai-bundled
codex plugin marketplace add $target --json
```

### 第四步：只修复不匹配的已安装版本

如果 marketplace manifest 正确，但 `InstalledMatch` 为 `False`，执行一次 `plugin add`。不要创建自动同步任务。

### 第五步：重启后按层验证

按以下顺序检查，可以避免把“Chrome 未运行”误诊为“插件损坏”：

1. 健康脚本的 package、runtime、installed 版本；
2. 内置 Browser 打开 `https://example.com/`；
3. Chrome 是否正在运行；
4. Chrome 扩展是否安装并启用；
5. `check-native-host-manifest.js` 是否返回 `correct: true`；
6. Chrome 真实导航烟雾测试。

## 快速判断表

| 现象 | 优先检查 | 正确动作 |
|---|---|---|
| Browser 和 Chrome 同时消失 | 当前 marketplace 是否注册并存在 | 先物化当前市场，再切换注册 |
| RuntimeMatch 为 `False` | AppX runtime 是否缺失或加密 | 使用 runtime repair，禁止覆盖无效既有目录 |
| RuntimeMatch 为 `True`、InstalledMatch 为 `False` | 已安装记录和缓存版本 | 一次性 `plugin add` |
| 扩展正常、Native Host 缺失 | Desktop 运行时和启动对账 | 修复运行时后重启 Desktop，不手写注册表 |
| Native Host 正确、Chrome unavailable | Chrome 进程和所选 Profile | 启动正确 Profile 后重试 |

## 不要做的事情

- 不要恢复自动同步或计划任务。
- 不要周期性执行 `codex plugin add chrome@openai-bundled`。
- 不要手工写 Native Host 注册表或 manifest。
- 不要运行历史 `installManifest.mjs`。
- 不要修改 WindowsApps 或向 AppX 包内写文件。
- 不要在新版市场验证完成前删除旧市场和插件缓存。
