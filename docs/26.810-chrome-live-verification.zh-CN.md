## 真实控制验证

1. 建立并命名临时 Chrome session。
2. 新建临时标签页并导航到 `https://example.com/`。
3. 读取标题 `Example Domain`，结果符合预期。
4. 关闭临时标签页，不保留测试页面。

这一步确认的不只是文件和注册表存在，而是 Chrome 扩展、Native Messaging Host、插件运行时和 Desktop 控制接口能够完成完整请求链路。

## 下次更新后的快速检查

1. 完全退出 Desktop 和托盘进程，重新打开一次。
2. 重新安装或启用 Chrome 扩展后，运行仓库健康检查脚本。
3. 对比 AppX、runtime marketplace 和已安装插件的三组版本；不要只看其中一组。
4. 检查 `com.openai.codexextension`，不要用旧的 `com.openai.codex` 作为判断依据。
5. 确认 Chrome 进程和正确 Profile 正在运行，再做一次真实导航烟雾测试。

## 不要做的事情

- 不要长期固定旧版 `openai-bundled` marketplace。
- 不要创建定时任务反复执行 `codex plugin add chrome@openai-bundled`。
- 不要手写 Native Host 注册表、manifest 或 `chrome\\latest` junction。
- 不要在没有物化和校验当前 AppX marketplace 前删除旧的可回滚注册。

## 根因判断

这次故障表现为扩展重新安装后仍无法使用，最终需要按层核对版本和运行时。核心原则是让当前 Desktop 管理其 AppX 专用 marketplace 和 Native Host；手工恢复只能作为一次性、经过校验的兼容措施，不能成为固定版本同步机制。
